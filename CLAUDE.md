# pixelforge

A reusable pixel art character, monster, combat and FX system. It produces tiny chibi sprites (the anchor is 11 x 18 px on a 32 x 32 canvas) in one locked style by layering hand-authored parts onto shared base animations per body plan (rig), recoloring them with material ramps, outlining the combined silhouette automatically, and exporting spritesheets with Aseprite-format JSON that includes combat data (phases, events, hitboxes, root motion). It will be used for fantasy combat with player characters and monsters across several games, so the core stays engine-agnostic.

## Sources of truth

- `style/anchor.png`: the reference sprite. When in doubt, match it.
- `style/style.json`: palette, materials, presets, canvas, pivot, outline, shadow, z-order, animation timing. Code reads it; never hardcode colors or geometry.
- `docs/STYLE_GUIDE.md`: what the style is, measured pixel by pixel.
- `docs/ARCHITECTURE.md`: how the system is built.
- `docs/ANIMATION_SPEC.md`: frame-by-frame specs for locomotion and core reactions.
- `docs/COMBAT.md`: combat animation set, phases, telegraph timing, events, hitboxes, FX library.
- `docs/MONSTERS.md`: rigs, size classes, monster materials, monster design rules and animations.
- `docs/QUALITY.md`: validator rules, review protocol, rubric, definition of done.
- `docs/ROADMAP.md`: phases, acceptance criteria, checkpoints, current status.
- `docs/GAMES.md`: what each game using pixelforge needs (Rolling Knight first) and the decisions it drove.

Read the relevant doc before starting a task. If a decision changes, update the doc in the same commit.

## Non-negotiable rules

1. Never resample, rotate, scale, blur or antialias art. Only integer translation and mirroring. Scaling for display or review uses nearest-neighbor only.
2. The palette is locked. Every opaque pixel comes from `style.json`. The only partially transparent pixels allowed are ground shadow pixels (outline color at alpha 70).
3. Outer outlines are generated by the compositor: 4-neighbor ring in #3a263a with open soles. Parts never draw their own outer outline. Outline-colored pixels inside parts are hand-placed details and are preserved.
4. One material per part file, plus the outline color. Two materials means two parts.
5. Every frame uses its size class: small is 32 x 32 with pivot (15, 27) and baseline row 27; medium, large and huge are in `style.json`. West is mirrored from East around the size class's axis (`x_new = 2 * axis - x`, so `30 - x` for small), never by flipping the canvas. Never upscale a sprite to make a bigger size class.
6. Art is reviewed by looking at it. After any art change, run `pf review` and open the images before saying anything about how it looks. Write down what you see, then judge it with the rubric in QUALITY.md.
7. `pf validate` and `pytest` must pass before every commit.
8. Stop at every CHECKPOINT in ROADMAP.md: show the human the review images, tell them how to open the preview, and wait for approval. Never start the next phase on your own. (Waived by the human on 2026-11-05: see the note at the top of ROADMAP.md.)
9. Commit after every working milestone with a clear message. Push to GitHub after each phase.
10. When an art decision is unclear, prefer the simpler option that reads better at 1x, and record the decision in the relevant doc.
11. Characters and monsters stay muted. Only FX (from `fx_ramps`) and glow eye presets may go brighter or more saturated. FX may be rotated in exact 90-degree steps; characters never.
12. Enemy attacks must meet their timing profile's telegraph minimum with a whole-body tell, and FX must never cover a tell.

## Workflow for any art task

1. Read the spec for what you're making (ANIMATION_SPEC.md, STYLE_GUIDE.md, the brief in ROADMAP.md).
2. Plan: which part files, which frames, which directions.
3. Draw or edit the PNG cells (write them programmatically pixel by pixel, or edit existing PNGs). Use `pf template` guides to align with the base body.
4. `pf build` then `pf validate`.
5. `pf review`, then open: turnaround, vs_anchor, sheet, diff strip, onion skin, silhouettes, 1x strip, exploded view. For combat animations add `--combat` and `pf battle`; for monsters also `pf roster`.
6. Describe what you see, score the rubric, list problems by priority.
7. Fix the biggest problem and repeat from step 4 until every rubric score is 4 or higher.
8. Commit and update the phase status in ROADMAP.md.

Drawing tip: when creating art in code, define each cell as a small character grid (like the pixel map in STYLE_GUIDE.md section 2) with a legend per material, and convert it to PNG. Grids are easy to reason about, diff, and fix one pixel at a time.

## Tech

- Python 3.11+, Pillow, numpy, PyYAML, typer (CLI entry point `pf`), pytest.
- Preview: static HTML and vanilla JS in `tools/preview`, served with `pf preview` (wraps `python -m http.server`). No frameworks, no build step.
- Art files are plain PNGs so the human can edit them in Aseprite.
- Setup: `python3 -m venv .venv`, then `.venv/bin/pip install -e ".[dev]"`. Run `.venv/bin/pytest` and `.venv/bin/pf` (or activate the venv). `pf` finds the repo from the current folder, or from `$PIXELFORGE_ROOT`.

## Commands

Fill these in as they get built. Built so far:

- `pf palette [--check] [--out PATH]` (Phase 0): checks every color ramp in `style.json` and writes `review/palette_swatches.png`; `--check` exits 1 on errors.
- `pf build <recipe>... | --all [--out DIR] [--no-gifs]` (Phase 1): composite, validate, export to `out/<name>/`.
- `pf validate [part folders or recipes]` (Phase 1): every rule; exits 1 on errors.
- `pf review <recipe> [--anim A] [--dir D] [--recolors]` (Phase 1): review images in `review/<name>/`.
- `pf anchors --check [--rig R]` (Phase 1): `review/anchors_<rig>.png`.
- `pf diff a.png b.png [--out PATH]` (Phase 1).
- `pf template <slot> <variant> <anim|rigid>` (Phase 4): an empty sheet and a `*_guide.png` with the base body and anchor_girl ghosted in.
- `pf random --seed N --count K` (Phase 4): random characters from `parts/compat.yaml` into `characters/random/`, built, with `review/random_<seed>_gallery.png`.
- `pf preview [--port N] [--bundle PATH]` (Phase 3a): serves the repo and opens at http://127.0.0.1:8000/tools/preview/ (views: #player, #gallery, #walk-test); `--bundle` writes one self-contained HTML file with every built character inlined.

Art is drawn in code as character grids by the scripts in `tools/art/` (run them with `.venv/bin/python tools/art/<script>.py`); the PNGs they write are canonical.
