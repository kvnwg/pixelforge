# Architecture

## 1. Goals

1. **Consistent by construction.** Every character shares the same base body frames, palette rules and outline pass, so style drift is structurally hard.
2. **Reusable.** One repo, many games. No engine-specific code in the core; exports are plain PNG + JSON.
3. **Hand-editable.** Every piece of art is a plain PNG a human can fix in Aseprite. No proprietary formats in the pipeline.
4. **Reviewable.** Every build can render images that make problems visible to both the human and Claude.
5. **Deterministic.** Same recipe + same seed = byte-identical output.

## 2. Concepts

| Term | Meaning |
|---|---|
| style | `style/style.json`: palette, materials, ramps, canvas, pivot, outline and shadow rules, z-order, animation timing |
| material | a named color ramp (skin, hair, cloth, leather, accent, eyes, metal) |
| preset | an alternative ramp for a material (e.g. hair: blonde) |
| slot | a layer category (hair_front, torso_wear, held_near...) |
| part | one variant in a slot (hair_front/long_straight), with its art and `part.yaml` |
| base body | the shared skin-only body that defines poses for every animation, plus anchor points |
| animation | idle, walk, attack, hurt, death, blink; each has frames per direction |
| anchor point | a named pixel on the base body per frame (head, hand_near, hand_far, back) used to position rigid parts |
| recipe | `characters/<name>.yaml`: which part goes in each slot and which preset each material uses |
| build | compositing a recipe into finished frames, validating, and exporting |
| rig | a body plan (humanoid, blob, quadruped, flyer...) with its own base body, anchors, slots, z-order, animations and size class (MONSTERS.md) |
| size class | small 32, medium 48, large 64, huge 96 px canvases, each with its own pivot and mirror axis |
| timing profile | player, enemy, elite or boss: scales hold frames so enemy attacks meet telegraph minimums (COMBAT.md) |
| phase | each frame of an attack is windup, active or recovery |
| event | a timed marker exported for the game: hit, spawn, vfx, recover... |
| hitbox / hurtbox | rectangles where an attack deals damage / where a character can be hit |
| fx | a reusable effect asset (smear, impact, projectile, status overlay) in `fx/` |

## 4. Sheets: how art is stored

Animated art is stored as one PNG per (part, animation): a grid of 32x32 cells.

- Rows are directions in the order `s, e, n` (row 0 = s, row 1 = e, row 2 = n). There is no `w` row because west is generated by mirroring.
- Columns are frames in order (column 0 = frame 0).
- A fully transparent cell means "this part draws nothing in this frame".
- Example: `parts/body/humanoid/walk.png` is 128 x 96 (4 frames x 3 directions).
- Combat animations follow `combat.view` (COMBAT.md section 0): with `side`, their sheets have a single `e` row.
- Cells are the size of the rig's size class (32, 48, 64 or 96 px).

This layout opens cleanly in Aseprite with a 32x32 grid, so a human can edit any frame directly.

`pf template <slot> <variant> <anim>` generates an empty sheet of the right size plus a `*_guide.png` with the base body (and the anchor girl, for reference) drawn at low opacity in each cell. In Aseprite, put the guide on a reference layer and draw the part on a layer above it.

## 5. Parts

### 5.1 Two kinds of parts

**Animated parts** have a sheet per animation and are drawn frame by frame, aligned to the base body. Use for anything that deforms with the pose: clothes, long hair, legs wear, the base body itself.

**Rigid parts** are drawn once per direction (a 3-cell strip: s, e, n) and are translated each frame so their origin pixel sits on a base body anchor point. Use for things that move with the body but don't deform: helmets, hats, short hair, held items at rest.

A rigid part may provide animated sheets for specific animations (for example a sword is rigid for idle and walk but needs drawn frames for attack, since art is never rotated).

Held items (Phase 5) do this with **pose cells** instead: one cell per direction for each pose a frame can ask of them, drawn in the same idle-hand coordinates as `rigid.png`, so the compositor moves them with the hand like the rest cell:

- `pose_<name>.png`: the item in that pose, at its usual z-order place.
- `pose_<name>_behind.png`: the item drawn behind the whole character (a sword cocked behind the head shows only where it sticks out). A pose with only a behind cell has nothing in front.
- `smear_<name>.png` (held_near only): the strike's smear, composited after the outline on empty pixels only, never outlined, so it can't cover the body.
- `hitboxes.json`: hitboxes per pose and direction, and named points per pose (`weapon_tip`, `bow_nock`, `shield_front`), in idle-hand coordinates (COMBAT.md section 4).

The base body's frames name the pose each held item takes (`"pose": {"held_near": "strike", "held_far": "guard"}` in anchors.json); trims follow their parent slot's pose; an item without that pose uses its rest cell. `tools/art/weapons.py` draws every pose as clean pixel lines in the item's shades (2:1 and 1:2 slopes in pixel pairs) and checks each against every frame that uses it, so no pose runs off the canvas or past x = 28 facing e (west mirrors x to 30 - x).

### 5.2 `part.yaml`

```yaml
slot: hair_front
variant: long_straight
rigs: [humanoid]          # rigs this part fits
material: hair            # exactly one material (plus outline color)
kind: animated            # animated | rigid
# for rigid parts:
# attach: head            # anchor point name on the base body
# origin: [15, 13]        # pixel in this part's cell that lands on the anchor point
# animated_overrides: [attack]   # rigid part with drawn frames for these anims
hides: []                 # slots this part hides, e.g. a helmet hides [hair_front]
lags: true                # this part trails the upper body by one frame (hair locks)
allow_singletons: []      # pixel coords allowed to be isolated (e.g. a highlight); a list,
                          # or a map per direction, in frame-0 coordinates
pose_singletons: {}       # the same per pose cell: {pose_draw: {e: [[x, y]]}} (bow tips)
# origin: auto            # rigid parts: 'auto' (default) means the cell is drawn in place for
                          # idle frame 0, so the origin is the attach anchor in that frame
notes: "Anchor girl's hair."
```

### 5.3 Rules for part art

- Use only the base ramp of the part's material, plus the outline color for hand-placed details. The validator rejects anything else.
- Do not draw the outer outline. The compositor generates it for the final combined silhouette, which guarantees one clean 1 px outline no matter how parts are combined.
- Draw what's hidden too, where it matters. The head under the hair must still be a complete head shape, so a short-hair or bald variant works without redrawing the body.
- Keep each part's pixels on the same grid positions as the base body for that frame. Animated parts follow the base body's pose offsets exactly (see ANIMATION_SPEC.md).

## 6. Base body and anchor points

Every rig has its own base body (`parts/body/<rig>/`). For the humanoid rig it is skin material only: a complete bald, unclothed mannequin (head, torso, arms, legs) in every pose. Everything else layers on top. It is split into three slots so clothing can sit between body and arms in side views: `body` (head, torso, legs), `arm_near`, `arm_far`.

`anchors.json` stores named points for every frame:

```json
{
  "idle": {
    "s": [
      {"head": [15, 14], "hand_near": [11, 23], "hand_far": [19, 23], "back": [15, 21]},
      {"head": [15, 15], "hand_near": [11, 24], "hand_far": [19, 24], "back": [15, 22]},
      {"head": [15, 15], "hand_near": [11, 24], "hand_far": [19, 24], "back": [15, 22]},
      {"head": [15, 14], "hand_near": [11, 23], "hand_far": [19, 23], "back": [15, 21]}
    ],
    "e": [ ... ],
    "n": [ ... ]
  },
  "walk": { ... }
}
```

(The numbers above illustrate the shape of the data; the real values come from drawing the base body.)

- `head` is a fixed reference pixel on the head (choose the top-center of the skull fill and keep that definition for every frame).
- Hands are the pixel where a held item's grip sits.
- The humanoid also has `hip` (the first leg row: everything above it is the upper body, used by the change-budget rule W2), `chin` (the chin row, used by the head-height rule E10), `torso` (the collar center: clothing, belts and tabards attach here), `back` (where a cape hangs), `foot_near` and `foot_far` (the bottom-center pixel of each foot), and a `planted` list naming the feet that carry weight in that frame (used by the jitter rule W1).
- Facing s, the near arm, hand and foot are the character's right: the viewer's left.
- Combat frames (Phase 5) also carry `shield_front` (where a guard is struck when no shield names its own) and `pose`, the pose each held slot takes.
- `pf anchors --check [--anim A]` renders every frame with anchor points marked, so wrong anchors are obvious.

A rig may name **default parts** in `style.json` (`rigs.<rig>.defaults`): every recipe on the rig gets them unless it names its own. The humanoid's default `held_near` is `fist`: no art, only the unarmed strike smears, reach hitboxes and the fist as `weapon_tip`.

## 7. Layer order

Z-order comes from `style.json` (`z_order.s`, `z_order.e`, `z_order.n`), bottom to top. Defaults:

- **s:** shadow, back, hair_back, body, legs_wear, feet, torso_wear, over_torso, belt, belt_trim, arm_far, held_far, arm_near, hands, hair_front, hair_locks, eyes, headwear, headwear_trim, held_near, held_near_trim
- **e:** shadow, held_far, arm_far, back, body, legs_wear, feet, torso_wear, over_torso, belt, belt_trim, hair_back, hair_front, hair_locks, eyes, headwear, headwear_trim, arm_near, hands, held_near, held_near_trim
- **n:** shadow, held_far, held_near, held_near_trim, body, legs_wear, feet, torso_wear, over_torso, belt, belt_trim, arm_far, arm_near, hands, hair_front, hair_locks, hair_back, headwear, headwear_trim, back

Notes: in the N view, `hair_back` is drawn over the head because it's what you see from behind, and a cape (`back`) goes over everything except headwear. Arms are above clothing in S and N because they hang beside the torso. In E, the near arm and its held item are in front of everything.

`hides`: a part can hide other slots (a helmet hides `hair_front`, `hair_locks` and `hair_back`). Hidden slots are skipped entirely.

Trim slots (added in Phase 4): `headwear_trim` (a plume), `belt_trim` (a buckle) and `held_near_trim` (a hilt, an orb, a spearhead) hold the second material of a two-material item, since every part has one material. Facing s, `held_far` sits just above the far arm, so a shield on it is in front of the body (the kit first had it behind the body, where a shield barely showed). Eyes sit above `hair_locks` so a lowered lock never hides an eye.

`hair_locks` (added in Phase 1): the loose hair in front that trails the head by one frame. Facing s these are the outer locks framing the face (ANIMATION_SPEC.md section 2); `hair_front` holds the rest of the front hair, which moves with the head. A slot of its own keeps `lags` a whole-part setting.

Rigid parts are drawn once per direction in their idle frame 0 place and follow an anchor: hair, eyes and headwear follow `head`; dresses, tabards and belts follow `torso`. Only parts that deform with the pose (the base body, arms, legs wear, boots, gauntlets) and held items in attacks are drawn per frame.

```yaml

  hair_front: none
  hair_back: none
  eyes: dots
  headwear: great_helm
  torso_wear: plate
  over_torso: tabard
  belt: leather_belt
  legs_wear: greaves
  feet: boots
  hands: gauntlets
  held_near: sword
colors:
  skin: light (anchor)
  metal: steel
  cloth: crimson
  leather: dark
  accent: gold (anchor)
  eyes: dark
anims: [idle, walk, blink, combat_idle, attack_slash, attack_heavy, block_enter, block_hold, block_impact, hurt, death, victory]
```

`characters/anchor_girl.yaml` must rebuild the anchor exactly (see ROADMAP Phase 1).

Randomizer: `pf random --seed N --count K` picks a part per slot from allowed variants and a preset per material, respecting `hides` and `parts/compat.yaml`: weighted hairstyles (one hairstyle sets up to three hair slots), weighted variants per slot, trims that follow their parent part (a sword gets a hilt), `requires` (a tabard needs plate or a tunic) and `incompatible` pairs (a bun under a tall hat). It redraws any character that would use more than 16 colors in any idle or walk frame, and writes the recipes it generated to `characters/random/` so a good one can be kept. Same seed, same characters.

## 9. Compositing pipeline

For each animation, each direction in `s, e, n`, each frame:

1. Resolve the recipe: the base body slots, then the rig's default parts, then the recipe's parts (skip slots hidden by other parts).
2. For each part, get its cell for this (anim, dir, frame). Rigid parts: take the direction cell (or the pose cell the frame asks for) and translate by `anchor - origin`. Parts with `lags: true` use the previous frame's offset, moved at most 1 px behind the current one (frame 0 uses the last frame's offset for loops); drawn parts with `lags: true` use the previous frame's cell. Held items posed behind the character go first, under everything. In grounded frames every layer but the held items is cut at the baseline.
3. Recolor the cell: map each pixel of the part's material base ramp to the recipe's preset ramp (index to index). Outline-colored pixels pass through.
4. Stack the cells in z-order with binary alpha (a pixel is either fully replaced or untouched). Keep a record of which pixels are hand-placed outline pixels.
5. Compute the silhouette: every opaque pixel that is not outline-colored.
6. Generate the outline (section 10) and draw it in the outline color.
7. Restore hand-placed outline pixels.
8. Composite the result over the shadow layer (shadow drawn from `style.json`, never outlined).
9. Apply effects flagged for this frame (closed eyes for blink and `eyes_closed` frames), then draw the held item's smear on empty pixels, then the flash.
10. Record the frame's combat data: named points (rig anchors plus the held items' pose points), the hurtbox (body pixels without held items or smears) and, on active frames, the held item's hitboxes for its pose, moved with the hand and clipped to the canvas.
11. Run per-frame validation.

After compositing, frame durations are retimed for the recipe's timing profile (COMBAT.md section 2).

Then mirror every finished `e` frame into `w` (section 12), run animation-level validation, and export.

## 10. Outline algorithm

```
silhouette = opaque pixels that are not outline-colored (shadow excluded)
ring = transparent pixels with a silhouette pixel directly up, down, left or right
lowest = lowest row containing silhouette or hand-placed outline
for each pixel p in ring:
    touches_only_from_above = silhouette above p, and not left, right or below
    if touches_only_from_above and p.y >= lowest - 2:
        leave p open            # open soles: ground shadow shows here
    else:
        draw outline at p
draw all hand-placed outline pixels
```

Unit test: run this on `style/anchor.png` with its outline pixels removed except the four hand-placed ones listed in `style.json` (`anchor.hand_placed_outline`). The result must equal `style/anchor.png` exactly.

Grounded frames measure open soles from the baseline rather than the lowest silhouette row, in a band from `baseline - 2` to `baseline + 1` (the row under the feet). For the anchor that is the same thing; it matters when a held item hangs below the feet: a sword tip keeps a closed outline instead of moving the soles down. Airborne frames get no open soles.

## 11. Recoloring

- Each material has a fixed number of shades (skin 3, hair 3, cloth 2, leather 3, accent 2, eyes 1, metal 4).
- A preset must have exactly that many shades.
- Recolor maps base shade i to preset shade i. Because each part declares one material, colors shared between materials (eyes vs cloth, leather vs hair) never collide.
- `pf palette --check` verifies every preset against the constraints in `style.json` (L range, C max, step size, hue shift direction) and renders a swatch sheet. Hard limits are errors; step size and hue shift are warnings, and known deviations are accepted in `constraints.accepted_ramp_warnings` (STYLE_GUIDE.md section 4).

## 12. Mirroring

`w` frames are produced from finished `e` frames: `x_new = 2 * axis - x`, where the axis is the size class's mirror axis (15 for small, so `x_new = 30 - x`; 23, 31 and 47 for medium, large and huge). Pixels that would land outside the canvas are a bug (the validator's bounds rule catches it). Mirroring happens after outlining, effects and validation of `e`, so `w` is always a perfect mirror.

## 13. Effects (no art needed)

- **flash:** every non-outline, non-shadow pixel becomes `effects.flash` (#efe2c8). Used in frames listed in `flash_frames`.
- **blink:** a one-frame `blink_<dir>` animation exported alongside idle: idle frame 0 with each eye pixel replaced by skin shadow. The game swaps it in every 2.5 to 5 seconds.
- **dissolve:** optional death despawn. 4 frames using a 4x4 Bayer matrix, removing 25%, 50%, 75%, then 100% of pixels (outline included).

## 14. Export

Per character, in `out/<name>/`:

- `<name>.png`: spritesheet. Rows are (animation, direction) in the order animations are listed in the recipe, directions `s, e, n, w`; columns are frames, left-aligned, 32x32 cells, no padding.
- `<name>.json`: Aseprite JSON (array format) so it loads in Phaser (`this.load.aseprite` + `this.anims.createFromAseprite`) and in Aseprite importers for other engines:

```json
{
```

## 16. Preview tool

`tools/preview/index.html`, plain HTML + JS, reads `out/index.json`:

- Character, animation and direction pickers, plus an "all 4 directions" view
- Zoom 1x, 2x, 4x, 8x with `image-rendering: pixelated`
- Backgrounds: beige, light, dark, checkerboard
- Play / pause, step frame by frame, true durations
- Toggles: onion skin, pivot and baseline, grid, side-by-side with the anchor
- Gallery mode: every built character's idle at 2x in a grid
- Movement test: the character walks across a strip at a configurable speed, to judge foot sliding
- Random blink while idle (the game's behavior: blink_<dir> for 100 ms every 2.5 to 5 s)

- Arena (Phase 5): a fighter attacks a training dummy with hit stop, flash, knockback, the attack's FX (Phase 6), hit and hurt boxes, a spell element picker for `cast`, and a timing profile toggle that retimes the attack from the exported holds (COMBAT.md section 9)
- FX (Phase 6): every FX in the library playing on the chosen ground at 1x, 3x or 6x; the player view also draws status overlays and `vfx` events

Views are routed by the hash: `#player`, `#gallery`, `#walk-test`, `#arena`, `#fx`. `pf preview --bundle out.html` inlines `out/index.json`, every character's JSON and PNG, and the anchor, so the same page works as a single file (and can be published as a page) with no server.

## 17. Review renders

`pf review` writes these into `review/<name>/`. Claude opens them after every art change; they're described in detail in QUALITY.md.

- `<anim>_<dir>_sheet.png`: frames at 8x with grid, frame numbers, durations, baseline and pivot marked
- `<anim>_<dir>_onion.png`: each frame with the previous frame ghosted behind it
- `<anim>_<dir>_diff.png`: changed pixels between consecutive frames (added green, removed red, recolored yellow), with counts
- `<anim>_<dir>_silhouette.png`: solid silhouettes, to judge readability of shape alone
- `<anim>_strip_1x.png`: every direction and frame at true size on beige, light and dark backgrounds, plus 2x
- `turnaround.png`: idle frame 0 in s, e, n, w at 8x
- `vs_anchor.png`: this character next to the anchor at 8x, plus a palette usage report
- `exploded_<dir>.png`: each layer on its own in z-order, then the composite
- `<anim>_<dir>_timeline.png` (`--combat`): frames under a time bar proportional to duration, colored by phase, with event markers, event points circled, hitboxes red and hurtboxes blue
- `review/battle/battle_<a>_vs_<b>_<anim>.png` (`pf battle`): the attack against a defender who reacts from the hit on

## 18. Tests

- Outline reproduction test on the anchor (section 10)
- `anchor_girl` recipe rebuilds `style/anchor_with_shadow.png` exactly as `idle_s` frame 0
- Mirror test: `w` equals mirrored `e` for every frame
- Recolor round trip: recoloring to the base presets is a no-op
- Validator tests: hand-made broken sprites (gap in outline, stray pixel, off-palette color, baseline drift) must each trigger the right rule
- Determinism: building the same recipe twice gives identical bytes
- Export test: JSON frame rects and tags match the sheet
- Combat data test: every attack has windup, hit (or spawn) and recover events, hitboxes only on active frames, and enemy-profile builds meet telegraph minimums (`tests/test_combat.py`, with E15 to E18 and W8 triggered on purpose)
- Size class test: a medium-class test sprite mirrors around x = 23 and exports with pivot (23, 43)

## 19. Extending

- **New part:** `pf template`, draw it, write `part.yaml`, add it to `compat.yaml` if needed, build a test recipe, review.
- **New animation:** add timing to `style.json`, write its spec in ANIMATION_SPEC.md first, draw the base body frames and anchors, then every animated part needs that sheet (the validator lists missing sheets).
- **New material:** add it to `style.json` with base ramp and presets, run `pf palette --check`.
- **New style (different game look):** copy `style/` to a new style folder and point recipes at it. Keep code style-agnostic so this works.

## 20. Rigs, size classes, combat data and FX

- **Rigs** are folders under `parts/body/<rig>/` with their own `anchors.json`, z-order (in `style.json` under the rig, falling back to the defaults), and animation list. The compositor, outliner, validator and exporter are rig-agnostic: they read canvas size, pivot and mirror axis from the rig's size class. Specs per rig are in MONSTERS.md.
- **Combat data** (phases, events, hitboxes, hurtboxes, root motion, timing profiles) is defined per animation in `style.json` and per weapon in held-item parts, and exported in `meta.pixelforge`. Rules and formats are in COMBAT.md.
- **FX** live in `fx/<name>/` with `fx.yaml` (ramp, tints, pivot, cell size, loops, layer above or below, follow or world-space, the anchor it rides) and one sheet per animation, authored facing east (`src/pixelforge/fx.py`, COMBAT.md section 6). They are built and validated separately from characters, against `fx_ramps` and `fx_constraints`, and exported as their own sheets plus JSON with every direction: west mirrored, south and north turned in exact 90-degree steps when the FX may rotate; characters never are. Character exports carry per-frame named points (`meta.pixelforge.points`) and status overlays (`overlays`) so a game can attach FX to anchors.
- **Draft examples** in `style/examples/` (slime, battle mockup) were drawn to prove the style extends to monsters and FX. They are references, not ground truth; the anchor is the only ground truth.
